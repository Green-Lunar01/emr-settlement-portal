Yes. The easiest way to understand this EMR system is to think of it as a daily financial reconciliation and approval workflow.

The system is not simply a form where a cashier enters numbers. It is a controlled process that answers:

“What did the facility say happened today, what does TAP say actually happened, did they match, who reviewed the difference, and who finally approved the record?”

There are three main human actors, plus the system itself:

Cashier / Operations → enters the day's figures.
System → automatically compares EMR against TAP.
Facility Manager → supervises the cashier's submission.
Finance / Auditor → performs the final financial verification.
1. First, understand what EMR and TAP represent

Let's simplify the terminology.

EMR

The EMR record is what the facility reports for a particular day.

For example, on October 8:

Field	Value
Date	8 Oct 2026
Transaction count	1,250
Transaction amount	₦4,500,000
Facility	Ikeja Facility

The cashier is essentially saying:

"These are the transactions we recorded at our facility today."

TAP

TAP is the other source of truth.

It already contains transaction information generated by the underlying transaction system.

For example:

TAP data	Value
Transaction count	1,250
Transaction amount	₦4,500,000

The EMR system compares these two sources.

So conceptually:

                CASHIER
                   |
                   v
             EMR RECORD
                   |
                   |
                   v
        +---------------------+
        | Automatic Comparison|
        +---------------------+
             /           \
            /             \
        MATCH           MISMATCH
          |                 |
        GOOD          CHECK RECORD
          |                 |
          +--------+--------+
                   |
                   v
            FACILITY MANAGER
                   |
                   v
              FINANCE
                   |
                   v
             FINAL DECISION
2. Why are there three people involved?

This is probably the most important business concept in the whole application.

It uses separation of duties.

The person who enters the information should not be the only person who approves it.

Think about accounting.

If I tell you:

"I collected ₦5 million today."

and I am also allowed to approve my own statement, there is no meaningful control.

Instead:

Cashier
  |
  | records
  v
EMR
  |
  | supervises
  v
Manager
  |
  | financially verifies
  v
Finance

Each person has a different responsibility.

3. The Cashier's job

The cashier starts the process.

They go into something like:

Daily EMR

They select the relevant date/facility and enter the day's figures.

For example:

Date:              08/10/2026
Transaction Count: 1,250
Transaction Amount: ₦4,500,000

The important thing is:

The cashier is responsible for entering the data.

But:

The cashier does NOT get to declare the data correct.

That distinction is fundamental.

4. The cashier submits the record

Before submission, the cashier can probably make changes.

The record might look like:

Status: DRAFT

The cashier can:

Create
   ↓
Edit
   ↓
Review
   ↓
Submit

Once they press:

SUBMIT

the system takes over the next step.

5. The system automatically compares EMR against TAP

This is where the system becomes more than a simple CRUD application.

Suppose the cashier entered:

EMR

Transaction count: 1,250
Transaction amount: ₦4,500,000

And TAP says:

TAP

Transaction count: 1,250
Transaction amount: ₦4,500,000

The system compares:

EMR count       == TAP count
EMR amount      == TAP amount

Everything matches.

Therefore:

SYSTEM STATUS = GOOD
6. What happens when the numbers don't match?

Suppose the cashier enters:

EMR

Transaction count: 1,250
Transaction amount: ₦4,500,000

But TAP says:

TAP

Transaction count: 1,247
Transaction amount: ₦4,485,000

The system detects:

Count mismatch
Amount mismatch

So instead of:

GOOD

the system displays:

CHECK RECORD

This does not necessarily mean the cashier is wrong.

It means:

"The two sources don't agree. A human needs to investigate."

That's an important distinction.

The system is performing validation, not making the final business decision.

7. What exactly is the Manager doing?

After submission, the Facility Manager gets the record.

The Manager should be able to see something like:

Daily EMR
────────────────────────────

Date: 8 Oct 2026

EMR
Transaction Count: ₦1,250
Transaction Amount: ₦4,500,000

TAP
Transaction Count: ₦1,247
Transaction Amount: ₦4,485,000

System Result
CHECK RECORD

Difference
Transaction Count: 3
Transaction Amount: ₦15,000

Cashier: John Doe

The manager investigates the situation.

Then the Manager has two choices:

CONFIRMED

or

NOT CONFIRMED

And can provide a comment.

For example:

"Reviewed the discrepancy. Three transactions were recorded in the facility EMR but had not yet reflected in TAP at the time of submission."

8. Manager confirmation is different from system validation

This is another important distinction.

There are two different decisions.

System decision
GOOD

or

CHECK RECORD

This is automatic.

Manager decision
CONFIRMED

or

NOT CONFIRMED

This is human.

Therefore you could have:

System: CHECK RECORD
Manager: CONFIRMED

That's completely possible.

The manager might understand why the discrepancy occurred and accept the cashier's submission.

Likewise:

System: GOOD
Manager: NOT CONFIRMED

could also happen if the manager notices another issue that the automatic comparison doesn't detect.

9. What happens after the Manager confirms?

This is where the locking mechanism becomes important.

Once the Manager confirms:

Cashier
   |
   | submitted
   v
Manager
   |
   | CONFIRMED
   v
LOCKED

The cashier should no longer be able to edit the record.

Why?

Because otherwise you could have:

Cashier submits ₦4.5m
       ↓
Manager approves ₦4.5m
       ↓
Cashier changes it to ₦3m
       ↓
Finance sees ₦3m

That destroys the audit trail.

So:

Manager confirmation freezes the cashier's submission.

10. Finance now becomes responsible for final verification

After the Manager's decision, Finance gets involved.

Finance sees essentially the whole history.

For example:

EMR
₦4,500,000

TAP
₦4,485,000

System
CHECK RECORD

Manager
CONFIRMED

Manager Comment
"Reviewed discrepancy..."

Finance then performs the final financial review.

Finance has two options.

CONFIRMED

or

NOT CONFIRMED
11. If Finance confirms

This is the happy path.

The lifecycle becomes:

CREATED
   ↓
SUBMITTED
   ↓
AUTOMATICALLY COMPARED
   ↓
MANAGER CONFIRMED
   ↓
FINANCE CONFIRMED
   ↓
COMPLETED

At this point the record is considered fully verified.

Think of it as:

Cashier approval: ❌
Manager approval: ✅
Finance approval: ✅

The cashier doesn't approve anything.

The Manager provides supervisory approval.

Finance provides final financial approval.

12. What if Finance rejects it?

This is where the second workflow begins.

Suppose Finance notices:

EMR: ₦4,500,000
TAP: ₦4,485,000

and the Manager's explanation isn't sufficient.

Finance chooses:

NOT CONFIRMED

Now the record goes back to the Cashier.

Conceptually:

Finance
   |
   | NOT CONFIRMED
   v
Needs Correction
   |
   v
Cashier
13. The Cashier can now correct the record

The cashier sees that Finance rejected it.

They investigate and discover:

"I accidentally included ₦15,000 from another day's transaction."

They correct the EMR:

Old:
₦4,500,000

New:
₦4,485,000

Then they submit again.

14. The comparison runs again

This is important.

The system doesn't simply say:

"It was previously approved by the manager, so we're done."

No.

The corrected submission is treated as a new review iteration.

The system compares again:

NEW EMR
₦4,485,000

        vs

TAP
₦4,485,000

Result:

GOOD
15. Previous approvals are reset

This is a critical design requirement.

Imagine:

Version 1

Cashier submits
       ↓
Manager confirms
       ↓
Finance rejects

Then cashier changes the record.

You now have:

Version 2

Cashier submits corrected record

You cannot leave:

Manager = CONFIRMED

because the Manager approved the old numbers, not the new numbers.

Therefore:

Version 1
Manager: CONFIRMED
Finance: NOT CONFIRMED

        ↓ correction

Version 2
Manager: PENDING
Finance: PENDING

The record must go through the approval chain again.

16. Why Finance Resolution exists

This is another important part.

Finance isn't simply clicking:

NOT CONFIRMED

and walking away.

They need to document why.

For example:

Finance Resolution:

"Transaction amount exceeded TAP by ₦15,000 due to
incorrect inclusion of a previous day's transaction.
Cashier corrected the EMR and resubmitted."

This becomes part of the audit trail.

It answers future questions like:

Why was this record rejected?

Who identified the problem?

What was the problem?

What did the cashier change?

Why was it eventually accepted?

17. Finance Resolution is different from Manager Comment

You effectively have two different forms of commentary.

Manager comment

This represents the operational/supervisory perspective.

Example:

"Reviewed the cashier's submission and confirmed the discrepancy was caused by delayed TAP synchronization."

Finance Resolution

This represents the financial/audit perspective.

Example:

"Variance of ₦15,000 reconciled against delayed TAP posting. Corrected EMR received and verified."

So don't combine these fields into one generic comment field.

They represent different responsibilities.

18. The entire thing is basically a state machine

From a backend engineering perspective, this is probably the most useful way for you to think about the application.

The EMR record has a lifecycle/state.

Something like:

DRAFT
  ↓
SUBMITTED
  ↓
COMPARED
  ↓
MANAGER_REVIEW
  ↓
MANAGER_CONFIRMED
  ↓
FINANCE_REVIEW
  ↓
FINANCE_CONFIRMED
  ↓
COMPLETED

But there's another branch:

FINANCE_REJECTED
      ↓
CORRECTION_REQUIRED
      ↓
CASHIER_EDITING
      ↓
RESUBMITTED
      ↓
COMPARED
      ↓
MANAGER_REVIEW
      ↓
FINANCE_REVIEW
19. I'd actually model it slightly more carefully

One thing I would not do is have one giant status field trying to represent everything.

For example, avoid something like:

status = "MANAGER_CONFIRMED"

because you actually have several independent dimensions.

I'd think about it as:

EMR Record
│
├── submissionStatus
│
├── systemComparisonStatus
│
├── managerReviewStatus
│
├── financeReviewStatus
│
└── correctionStatus

For example:

submissionStatus:
SUBMITTED

systemComparisonStatus:
MISMATCH

managerReviewStatus:
CONFIRMED

financeReviewStatus:
PENDING

That gives you a much clearer representation.

21. Now think about permissions

The application isn't just displaying buttons based on role.

The backend should enforce the rules.

Cashier

Can:

CREATE EMR
EDIT OWN PENDING EMR
SUBMIT EMR
EDIT REJECTED EMR
RESUBMIT

Cannot:

CONFIRM
MANAGER APPROVE
FINANCE APPROVE
WRITE FINANCE RESOLUTION
Facility Manager

Can:

VIEW SUBMITTED RECORDS
VIEW TAP DATA
VIEW COMPARISON
CONFIRM
NOT CONFIRM
ADD MANAGER COMMENT

Cannot:

EDIT CASHIER'S EMR
WRITE FINANCE RESOLUTION
FINALIZE FINANCE REVIEW
Finance

Can:

VIEW EMR
VIEW TAP
VIEW COMPARISON
VIEW MANAGER REVIEW
CONFIRM
NOT CONFIRM
WRITE FINANCE RESOLUTION

And the document adds one additional responsibility:

CREATE CASHIER ACCOUNTS

That should probably be treated as a separate administrative permission even though Finance has it.

22. The most important security rule

Don't rely on the frontend.

For example, hiding the Edit button from the Cashier after Manager confirmation is not enough.

Someone could call:

PATCH /api/emr/123

directly.

The backend must check:

Is this user the cashier?

Is the record editable?

Has the manager already confirmed?

Has Finance rejected it and returned it for correction?

Is this actually the current review iteration?

Only then should the API allow the modification.

23. There's also an important concept: review iteration

This isn't explicitly emphasized in the document, but it is implied by:

"Resubmission resets the review process; previous confirmations do not automatically carry over."

That means your system should probably track submission/review versions or iterations.

For example:

EMR #123

Iteration 1
----------------
Cashier submitted
Manager confirmed
Finance rejected


Iteration 2
----------------
Cashier corrected
Manager confirmed
Finance confirmed

That is much safer than simply overwriting the original record.

It gives you an audit history.

26. So what are you actually building?

If you're implementing this as an engineer, don't think:

"I'm building a daily EMR form."

You're actually building:

A controlled financial reconciliation workflow with role-based approvals, automatic reconciliation against TAP, correction/re-submission capabilities, and a complete audit trail.

The important pieces are therefore:

Data
Facilities
Users
Roles
EMR records
TAP transactions
Comparison results
Manager reviews
Finance reviews
Finance resolutions
Audit logs
Workflow

→ Manager Review
→ Finance Review
→ Complete

Finance Rejects
→ Cashier Corrects
→ Resubmits
→ Compare Again
→ Manager Reviews Again
→ Finance Reviews Again
Security
Cashier ≠ Manager ≠ Finance
Auditability

Every important action should answer:
